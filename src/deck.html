I work like this too

I read the code out of curiosity, not to approve a change.

But cedo is not a weekend project: commits in days of work, in production, with several users, a public repository and an iPhone app.

Ghostty's AI policy: “The human-in-the-loop must fully understand all code.”

On a personal project I rely on tests and checks. At work I would read the code, as Ghostty asks.

Slop is code written faster than anyone can read it, understand it, or check that it works.

“They all looked good. They were formally correct. Tests and checks passed.” (tldraw, about the AI pull requests they closed)

What it leaves in a codebase:

  • complexity, duplication, dead code
  • tests that check nothing, code that is almost right
  • security holes, ignored conventions, decisions nobody wrote down
+41.6%

La mia tesi è che si può fare vibe coding senza produrre slop. Prima però chiariamo che cosa intendo per slop. Alla lettera è la sbobba; qui è il codice scritto più in fretta di quanto si riesca a leggerlo, a capirlo o a verificare che funzioni.

  • 0:30 tldraw ha chiuso le pull request generate con l'AI e lo ha spiegato così: sembravano tutte a posto, erano formalmente corrette, test e check passavano. È questo il problema dello slop: a prima vista sembra buono.
  • A sinistra, quello che lascia in una codebase. Non leggere l'elenco: lo riprendo più avanti, voce per voce.
  • Due numeri soli, poi basta. Nei progetti che hanno adottato Cursor la complessità del codice è salita del 41,6% e non è più scesa. E il 45% del codice generato non ha passato i test di sicurezza di Veracode.

The same access check had to be fixed five times

It was a condition repeated by hand in every query.

Now it is in one place, and lint and two tests make sure nothing skips it:

  • every read goes through a function like visibleWorkouts(caller)
  • lint fails if code imports one of the protected tables directly
  • a test fails if raw SQL names one of them
  • another test calls every GET route and MCP tool as a user who has just been removed from a group
docs/adr/0019-visible-relations.md, 16 October; db/visible.ts, db/raw-sql.test.ts, test/membership-lost.test.ts
  • 0:00 Seconda domanda: che cosa lo rende sicuro? In cedo i dati sono condivisi: ci sono gruppi, membri, e persone che a un certo punto vengono tolte da un gruppo. La regola su chi può vedere che cosa era una condizione da ripetere a mano in ogni query.
  • È stata dimenticata o scritta male cinque volte. Ogni correzione era giusta, ma il problema stava a monte: una regola che funziona solo se ti ricordi di applicarla.
  • 0:40 clic Adesso la condizione sta in un posto solo. clic Ogni lettura passa da una funzione che restituisce soltanto le righe che quell'utente può vedere. Se il codice importa direttamente una di quelle tabelle, fallisce il lint. Se le nomina in una query SQL scritta a mano, fallisce un test.
  • 1:10 E un altro test toglie un utente da un gruppo e poi chiama, a nome suo, tutte le rotte GET e tutti i tool MCP. Serve contro lo stesso tipo di buco che ha avuto Lovable: 170 app esposte perché mancava la row-level security.

  • 0:00 Ogni struttura dati è definita una volta sola, come schema Zod, in un pacchetto condiviso. La rotta HTTP lo usa per validare il body, il tool MCP come schema di input, l'app come tipo della richiesta.

  • 0:50 clic Qui però abbiamo scoperto che un test verde non dimostra niente, se non l'hai mai visto fallire. Altri due continuavano a passare anche dopo che avevamo cancellato apposta il controllo che dovevano verificare.
  • Da allora, prima di fidarsi di un test lo si lancia sul codice sbagliato e lo si guarda fallire. È scritto nelle note del progetto, e l'agente lo fa da solo.

Each kind of slop, and what stops it

Complexityfiles capped at 300 lines; five import rules in lint
Duplicationeach data shape is defined once, as a Zod schema
Dead codenothing checked for unused code across filesknip runs in the gate: it found unused exports
Tests that check nothingevery new test must first fail on the unfixed code
Code that is almost righta review by a new agent after each piece of work
Security holesaccess functions, a raw-SQL scan, a test for every route
Hallucinated packagesnothing checked a new packageeach needs a written reason and a version at least a week old
Ignored conventionsunit conversions belong in one file, but only review checkeda test finds conversions outside that file: moved
Decisions nobody wrote downquestions first, then an ADR and the glossary
Untested codecoverage was never measured files measured; each needs 90% coverage

Five things to copy on Monday

  1. Set up the gate before the first feature.Prevents: code piling up faster than anyone checks it.
  2. Turn each rule into a lint rule or a test, with an error message written for the agent.Prevents: ignored conventions and growing complexity.
  3. See every new test fail before you rely on it.Prevents: tests that check nothing.
  4. Have a new agent, with no context, review each piece of work.Prevents: code that is almost right, and code that nobody reviews.
  5. Have the agent ask you questions first, and keep the answers in the repo.Prevents: undocumented decisions, and an agent that starts every session knowing nothing.

Se lunedì volete provare, queste sono le cinque cose che copierei. Ognuna serve contro uno dei tipi di slop che abbiamo visto.

  • 0:20 Uno: il gate va messo in piedi prima ancora di scrivere la prima feature. Il mio primo commit non conteneva nessuna feature: solo le regole e i controlli.
  • Due: ogni regola deve diventare una regola di lint o un test, con un messaggio di errore pensato per l'agente.
  • Tre: ogni test nuovo va visto fallire. Quattro: alla fine di ogni pezzo di lavoro, una review fatta da un agente che parte da zero. Cinque: fatevi fare le domande dall'agente, e lasciate le risposte scritte nel repository.

Quindi sì, si può fare vibe coding senza produrre slop, a patto che il progetto non accetti codice finché non si è dimostrato che funziona. La qualità di cedo, per me, dipende da questi controlli più che dall'agente.

The query count must be the same for a page of 5 and a page of 50, on 250,000 logged sets.

  • Il test non misura i tempi, che cambiano da una macchina all'altra. Controlla due cose: che il numero di query resti lo stesso con 5 o con 50 righe, così un N+1 salta fuori subito, e che Postgres usi gli indici invece di scorrere tutta la tabella.

The deploy key can run only one command

scripts/deploy-ssh.shread -r verb sha extra <<<"${SSH_ORIGINAL_COMMAND:-}"
if [[ ${verb:-} != deploy || ! ${sha:-} =~ ^[0-9a-f]{40}$ || -n ${extra:-} ]]; then
  echo "usage: deploy <40-character commit sha>" >&2
  exit 64
fi
git fetch --quiet origin main
if ! git merge-base --is-ancestor "$sha" origin/main; then
  echo "$sha is not on main: refusing to deploy it" >&2
  exit 65
fi
  • La chiave SSH che la CI usa per il deploy può fare una cosa sola: chiedere il deploy di un commit che sta su main. Qualsiasi altro comando viene rifiutato.
